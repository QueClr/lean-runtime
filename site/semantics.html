The Nat, Int and String rules and Float.scaleB follow one pattern. The short common case is inline. The rare case is in a function marked #[cold] and #[inline(never)]. So a translator can call the function for every value, and the code it inlines stays small.

Nat and Int

Lean's C runtime splits big-number work in two parts. lean.h and object.cpp decide the rules; GMP only computes. lean-runtime keeps that split (decision Q4).

  • Rules are generic functions in lean-runtime. They decide what happens with a zero divisor, a truncating subtraction, an exponent or a shift amount.
  • Big-number arithmetic is a trait, BigNat (and BigInt). Each translator implements it with its own library: lean2rr with GMP, leanrs with malachite.
  • Word methods. For +, - and * of a word and a big Int, in either order, the rules call a word method of BigInt. They also call one to divide a big Int by a word, but not to divide a word by a big Int. Examples are add_i64, i64_sub and tdiv_i64. By default, the method makes the word a big number and calls the big operation. A backend can compute from the word directly, without that temporary number.
  • Two layers. Word helpers (*_small) take u64 or i64 values and give the exact result, for a translator's own fast path. Rules take Nat<B>: a word (Small) or a big number (Big) of the backend B.
  • Normalization. Each translator normalizes results with its own boundary. Both keep a Nat below 263 in a word.
  • MAX_BITS is the backend's largest result, in bits. leanrs's is 239 bits. lean2rr's is about GMP's limit; it is set when lean2rr adopts the crate.
  • The size test. add, succ, mul, pow and shiftLeft know a bound on the result size before they compute. Above MAX_BITS they stop with INTERNAL PANIC: out of memory. When the exponent or shift is 232 or more, they print native's exponent message instead.
  • Lifted limits. Native Lean stops where the definition still has a value: Nat.pow or Nat.shiftLeft by 232 or more, for example. lean-runtime computes the definition's result there (LB-04, LB-11, LB-12).
  • Int division. Int.tdiv and Int.tmod round toward zero. Int.ediv and Int.emod keep the remainder in [0, |d|). A zero divisor gives the quotient 0 and the remainder the dividend.
  • The other Nat and Int functions (Nat.sqrt, Int.fdiv, the Int bitwise operations) are Lean code. The translators compile them.

Fixed-width integers

  • Most UIntN and IntN operations are one machine operation. Each translator emits them inline (wrapping + - *, bitwise operations, comparisons, casts).
  • lean-runtime holds the rest:
    • division and remainder by zero;
    • the signed comparisons and abs of IntN;
    • shifts, where the amount is taken modulo the width;
    • log2;
    • the conversions to and from Nat and Int, and to Float and Float32.
  • A signed value travels as its two's-complement bits in the unsigned type of its width, as in lean.h. A Nat argument travels as its value modulo 264.

Float, Float32 and libm

  • float and float32 hold what is not one Rust operator: toString, the saturating conversions to integers, ofBits/toBits, frExp, scaleB and the classification functions.
  • Float.toString is C's %f: six decimals, every integer digit, NaN, inf. It writes into a fmt::Write and allocates nothing. For a finite value below 253 in magnitude, to_string_fast_bytes gives the same text as bytes in the caller's buffer. A translator that copies bytes into its own string uses it, and does not check that the text is UTF-8.
  • libm has one function per C function (sin, pow, cbrtf and so on). Native Lean calls glibc's libm. Rust's f64 and f32 methods call the same libm, with the exceptions below.

The exceptions

  • Ports. Rust's cbrt and atanh (and their f32 forms) are not glibc's algorithms. lean-runtime has ports of glibc 2.39's code for them. cbrt and cbrtf give the results of glibc's aarch64 build on every target. atanh and atanhf use glibc's formula over the platform's log1p. On other platforms, the results can differ from native Lean on that platform, by the owner's choice of one algorithm.
  • Constant folding (why black_box). LLVM computes a libm call with constant operands at compile time. Its result can differ from glibc's in the last bit. For example, LLVM folds exp2(x) as pow(2, x), and it rewrites pow(x, 2.0) as x * x. Native Lean always passes run-time values to the C call. So exp2, pow, powf and every inexact f32 function pass their operands through core::hint::black_box. The call then stays a call, also after inlining.
  • Exact functions (fabsf, ceilf, floorf, roundf, sqrtf) fold to glibc's result and need no barrier.
  • The check. tests/libm_folding.rs calls every function on literal operands and on the same operands through black_box, in an optimized build. The two results must be equal, bit for bit.

The cost of black_box is on the list for the first timing session (O12).

Strings and UTF-8 positions

  • A String.Pos.Raw is a byte offset. The functions take the string's UTF-8 bytes and a u64 position.
  • Lean's C treats a position of 263 or more as a big number, which is always past the end. The caller passes such a position as u64::MAX (or as itself, if it fits).
  • Results are plain data: a u32 character, a u64 position, a byte Range. The caller builds its own string from a range.
  • The functions: get, next, prev, atEnd, isValid, extract, the byte-order comparisons, and others.
  • String.Pos.Raw.set (also String.Pos.set and String.set) returns a change, not a string. The change gives the byte range of the old character and the bytes of the new one. At an invalid position, there is no change, and the caller keeps its string without a copy. On a unique string, the glue applies the change in place. When both characters have the same size, write_in_place stores the new one. Otherwise the glue moves the tail of the string, if the block has room.
  • ByteArray.validateUTF8 accepts exactly the well-formed UTF-8 of the Unicode standard, as Lean's C validator does. It rejects overlong forms, surrogates and values above U+10FFFF.
  • utf8_strlen counts the characters of a new string: the bytes that are not continuation bytes. It counts eight bytes at a time in a u64. A translator keeps the count in its string object, as Lean does.
  • Substring.Raw's externs are Lean code, so they are not here.

IP addresses

Std.Net.Addr converts IP addresses to text and back. These functions need no event loop, so they are in semantics.

  • Natively, the C functions call libuv 1.48's own parser and formatter (src/inet.c), not glibc's. lean-runtime has ports of that code.
  • IPv4Addr.ofString accepts four decimal parts from 0 to 255, with no leading zero.
  • IPv6Addr.ofString accepts up to eight groups of hex digits, one ::, and an IPv4 address at the end. It drops a zone after %, as libuv does.
  • A string with a NUL byte gives none: Lean's C checks this first.
  • IPv6Addr.toString writes lowercase hex and replaces the first longest run of two or more zero groups with ::. It writes ::ffff:1.2.3.4 and ::1.2.3.4 with an IPv4 tail, as libuv does.
  • An address is plain data: four octets or eight 16-bit groups. The text goes into a fmt::Write.

Hashing

  • mixHash and MurmurHash64A, bit for bit as Lean's hash.cpp.
  • They are behind String.hash, ByteArray.hash and String.Slice.hash.
  • They decide the iteration order of Std.HashMap, and a program can print that order. So a different hash would change the output.

Arrays

The array functions take lengths and indices and return a decision. The translator carries out the decision on its own array.

  • xs[i]! and Array.set! out of bounds print Error: index out of bounds as a panic. Then they return the default value, or the array unchanged.
  • ByteArray.get!, FloatArray.get! and their set! out of bounds are silent: 0, 0.0, or the array unchanged.
  • Array.pop of an empty array gives the empty array.
  • The allocators stop with INTERNAL PANIC when a size overflows or is not a machine word.
  • ByteArray.copySlice follows its Lean definition, also for offsets of 264 or more (LB-06).

Text output

  • Some Repr and ToString definitions are Lean code that both translators replace with runtime code. lean-runtime holds that code once.
  • The texts: decimal digits for Nat.repr and Int.repr, USize.repr, Char.quote, String.quote, the test of Repr.addAppParen, and the Bool and Unit texts.
  • Text goes into a fmt::Write that the caller supplies.
  • The rest of Repr and ToString (structures, lists, Format) stays Lean code that the translators compile.

Toolchain facts

Three Lean functions report facts about the Lean build, not about the program. lean-runtime holds them as constants, with the values that native Lean 4.34.0 reports.

  • Lean.githash: the commit of the v4.34.0 tag.
  • Lean.version.specialDesc: empty, because 4.34.0 is a release.
  • System.Platform.target: the target triple, aarch64-unknown-linux-gnu on the pinned host. Native Lean on another platform reports that platform's triple. So lean-runtime builds the triple from the target that the program is built for.
