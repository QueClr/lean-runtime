Threads mode

Threads mode (feature threads) is Lean 4.34.0's task manager on real OS threads. It is the module sched::mt, which a threads build uses in place of the single-thread scheduler.

Threads mode came in three batches on 2026-10-04, and a fourth on 2026-10-05. T1 is the task manager, T2 is io and Std.Internal.UV on threads, T3 is the second test driver, and N is net on threads. The owner chose native's worker pool, and atomic values in every threads-mode program (2026-10-04). No translator uses threads mode yet. leanrs plans it; lean2rr stays single-threaded for now.

What the mode is

  • One scheduler per build. A translator chooses the mode when it builds a program. The feature threads excludes sched: a build with both is a compile error. The feature net goes with either scheduler (N).
  • The same names. A threads build re-exports sched::mt as sched. So the glue calls sched::spawn, sched::wait and the other functions by the same names in both modes.
  • What changes for the glue:
    • a job is Send, because a worker thread runs it and drops it;
    • the glue is an Arc<dyn Glue>, with Send and Sync;
    • the glue has five optional hooks: thread_start, thread_end, task_begin, task_end and workers_end;
    • there are no coroutines, so there is no Glue::suspend and no unsafe step in the glue.
  • Blocking calls. With io, a blocking call blocks only its own thread, as natively. The cooperative IO of sched-io belongs to the single-thread scheduler only.
  • Yield points are calls that do nothing in this mode.
  • No cost elsewhere. A build without threads does not change: it has no Arc and no new lock.

The worker pool

  • Workers. The pool has up to LEAN_NUM_THREADS standard workers, or one per online processor. The manager makes them when tasks need them.
  • Stacks. Every thread that the manager makes, and the loop thread, has Lean's stack size: 1 GiB, or LEAN_STACK_SIZE_KB plus 128 KiB. The io layer's own helper threads keep std's default size.
  • Dedicated tasks. A task with a priority above Task.Priority.max gets a thread of its own, whatever the size of the priority (LB-39).
  • One lock protects the task table and the queues, as in native's task manager.
  • Waits. A pool task that waits in Task.get or IO.wait raises the pool's limit by one while it waits. So waiting tasks cannot take every worker and starve the pool. The raised limit stops at its maximum, where native's limit wraps to 0 (LB-52). IO.waitAny keeps its worker, as natively.
  • Dependents. A sync dependent runs on the thread that finishes its source. The other dependents go to the queue. The waiters of a task wake when the walk of its dependents ends, as natively.
  • The loop thread. Std.Internal.UV's timers and signals run on a thread of their own, as natively (T2). That thread resolves their promises. With net, the sockets and the name lookups run there too (N).
  • Exit. After main, finish sets Lean's shutdown flag, and works in this order, as native's task manager does:
    1. It waits until the queue is empty and joins the standard workers. Their thread-locals, such as the streams a task left set, end there.
    2. It calls the glue's workers_end (AR-34).
    3. It waits for the dedicated tasks and joins their threads.
    Then the glue flushes the streams and exits.
  • Late tasks. A pool task enqueued during the shutdown gets a worker and runs. Natively it is lost once no worker is left (LB-13).

Values that cross threads

  • Atomic values. In a threads-mode program, every counted object is atomic (decision of 2026-10-04). Native Lean marks objects as multi-threaded only when they cross threads. Neither translator can do that, so both would make every count atomic.
  • Tasks. The glue's task object is an Arc with a OnceLock slot. The job fills the slot. The last drop of an unfinished task calls release, on any thread.
  • References. IO.Ref follows Lean 4.35's rule, as sched::Ref: a lock and a condition variable. While a modify function runs, get, take, set and swap wait for its store. So a set is never lost (LB-01). A swap never returns its own argument (LB-18).
  • Thunks and lazy constants block their thread with std's OnceLock, as native's lean_obj_once does.
  • Rust panics. A Rust panic in a job or in a hook ends the process with an abort, on any thread.

Networking

With the feature net, threads mode runs Std.Internal.UV's TCP, UDP and name lookups on the loop thread, as natively (N, 2026-10-05).

  • The loop lock. Each extern holds the loop lock from its start to its end, as natively. When the loop thread holds the lock, the extern interrupts the loop and waits for the end of its iteration. So the loop handles what is ready before the extern acts.
  • Callbacks. The loop thread reads, accepts and writes the rest of a send. It resolves the promises with the loop lock held, so their sync dependents run on the loop thread.
  • The last handle. The drop of a socket's last handle takes the loop lock, on any thread, and closes the socket at once. A pending operation holds the socket. So a socket that a worker drops during a receive stays open until the loop thread completes the receive.
  • Name lookups. Two helper threads call glibc, as in the single-thread mode. A helper gives its answer to the loop thread through a queue, without the loop lock.
  • Order. In each iteration, the loop thread runs the callbacks of the sockets first and the signal watchers last, as libuv does.
  • After the exit's wait the loop thread starts no callback, so no promise resolves. It checks before each callback, so only a callback that already runs then goes to its end. The single-thread scheduler's loop does not run then either. Natively a promise resolved then can crash the exit (LB-27).
  • One source. The TCP, UDP and DNS code is the same in both modes. A small mode layer gives the part that differs (mode_mt.rs, mode_st.rs).

Known differences

  • Native bugs are not copied. LB-01, LB-13, LB-18, LB-32 and LB-52 stay fixed, as in the single-thread scheduler. So do the loop's LB-19, LB-20, LB-33 and LB-34 (Lean bugs).
  • After the exit's wait there is no task manager, as natively. A few native calls then use a null manager. Here they give safe answers: a promise resolved then runs its dependents at once.
  • A native data race is avoided. Native Lean stores a bind task's next step without the lock. Here the store holds the lock.
  • A refused spawn. Where unshare(CLONE_FS) once worked, a later refusal makes the spawn fail with EAGAIN. Natively the forked child enters its directory itself.
  • The loop thread starts at the first use of Std.Internal.UV, not at the program's start.
  • Schedules. The order of racy output lines varies from run to run, as natively. Thread ids and the resident memory are not native's.
  • No LSCHED differences. The pure-task rule and its known differences (LSCHED-01 to LSCHED-03) are the single-thread scheduler's. In threads mode those cases give native's outcome.

How it is tested

  • Unit tests of sched::mt, also under Miri (opt-in), which finds data races.
  • The io and uvloop twins run inside tasks in a threads build (T2).
  • The second driver (T3), tests/sched-driver-mt, runs every case of tasks/, sync/, refs/ and taskio/, and since N of net/. It runs the same Rust ports as the single-thread driver. Cargo builds it alone, because one build cannot have both schedulers.
  • Five runs. The driver runs each case 5 times. Each run must give the recorded outcome or a recorded alternative. A new alternative is recorded only from native runs, never from the crate's own runs.
  • LSCHED cases. A case with a known difference of the single-thread scheduler accepts only native's outcome here.
  • Lean bugs. A case for a Lean bug must give the correct outcome in every run.
  • The hooks. The driver's glue checks the hooks' contract in every run. For example, a worker never begins a task inside another task.
  • Single-thread-only cases. A case whose port needs the single-thread scheduler would go in one list, with the reason. The list is empty: every case passes in both modes.
  • Cases with real contention (T3, recorded natively):
    • wait_chain_beyond_pool: six pool tasks on two workers wait on each other;
    • wait_any_faster: IO.waitAny returns the faster of two running tasks;
    • stack_overflow_in_dedicated: Lean's report on a dedicated task's thread;
    • late_tasks_while_enqueuing: the exit while a task still enqueues tasks (LB-13).
  • The network's own tests (N): unit tests drop a socket or cancel a receive on another thread while the loop thread waits for the socket.
  • The check. scripts/check.sh runs both drivers, in debug and release builds, on both toolchains.
