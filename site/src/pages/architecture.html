Architecture

lean-runtime has four modules. Cargo features select them. Each translator's glue connects its own values to the crate.

Features and dependencies

  • Default. semantics only. No dependencies, so a plain rustc --crate-type rlib build works (one translator does not use cargo).
  • io. Makes system calls through rustix and nix, and the io_uring rings at startup through io-uring. These crates hold the unsafe code, so io has none of its own.
  • sched. Switches stacks through corosensei. Its event loop uses rustix's epoll, and its signal watchers signal-hook's safe self-pipe. One unsafe step stays in each translator's glue: one dereference in Glue::suspend.
  • threads. Threads mode, in place of sched: Lean's task manager on real threads (sched::mt). Its task manager uses std's threads and locks only. Its loop thread for Std.Internal.UV uses rustix and signal-hook, as sched does. It has no unsafe code. It excludes sched and net: a build has one scheduler. The design and its status are in docs/threads.md.
  • net. Turns on io and sched. Its sockets use the net features of rustix and nix. Its name lookups call glibc through dns-lookup, pinned at 2.1.1. UNSAFE.md records the audit of that crate's unsafe code.
  • proc-title. Turns on io, and adds a native quirk with no safe route, in a file of its own. io::argv_title writes the process title into the arguments' memory (io). lean2rr turns it on. Without it, setProcessTitle fails with ENOBUFS.
  • startup-fds. Turns on io, and adds a native quirk in a file of its own. io::startup_fds is an ELF constructor that opens the startup descriptors before Rust's runtime starts (io). lean2rr turns it on. Without it, a translator's glue writes that constructor itself.
  • stack-overflow. Needs sched or threads, and adds a native quirk in a file of its own, with nix's sigaction. sched::stack_overflow is Lean's stack-overflow report for the stacks of the contexts (sched). lean2rr turns it on. Without it, a task that overflows its stack ends with a plain SIGSEGV (status 139).
  • unsafe-fast. Opt-in. It may enable a faster unsafe version of a function. That version must have the same behaviour as the safe one, a written proof in UNSAFE.md, and Miri checks. The safe version always stays.

Shared code and glue

The rule (decision 2026-10-03): lean-runtime holds every runtime function. A translator keeps only what its own value representation needs.

Some extern functions need no shared code. The coverage count of 2026-10-04 sorts Lean's 717 Init and Std extern symbols this way:

  • 171 are one machine operation that each translator emits inline (wrapping +, bitwise operations, casts).
  • 67 belong to the glue, because they depend on the translator's own objects or memory protocol. Examples: append, push, size, thunk and ref cells, sharing tests, heartbeats.
  • 27 are Lean code already (@[export] definitions).
  • The other 452 need shared code. The status page shows how many are done.

Views in, data out

No function in lean-runtime owns, allocates or frees a Lean value of either translator. So neither glue converts or copies bulk data.

  • Views in. Functions take &[u8], &str, u64 and f64. A path is the bytes of a Lean string.
  • Plain data out. A character is a u32, a position a u64, a substring a byte Range.
  • Text goes into a fmt::Write that the caller supplies (for example Float.toString).
  • Reads go into the caller's storage. read_uninit fills the bytes the caller allocated, with no zero pass. An unbounded result (a line, a path) is appended to a ByteSink that the caller implements on its own object.
  • Only the cold error path owns data: an IoError holds its file name and details as Strings.

Scope: Lean's own library

Decision (2026-10-03): the translators target Lean code only, with the runtime library as the one exception.

  • Only the externs of Lean's own library (Init, Std) are native code. lean-runtime supplies them.
  • Any other @[extern] runs its Lean definition by default. Its C code is never built or linked.
  • An extern without a Lean definition is refused when the program is translated.
  • A program extern that names a runtime-library symbol, with a matching signature, gets that runtime function, as native linking gives it.
  • So lean-runtime needs no boundary for user C code.

Builds and platform

  • Builds are offline and use no nightly features. The crate builds on the Rust toolchains of both translators.
  • Cargo.lock is committed. io builds with cargo build --offline --locked --features io, from cargo's local registry cache. The same command builds sched and net. Nothing is vendored.
  • A new dependency needs a check against leanrs's offline registry. A new crate that wraps unsafe needs the owner's decision.
  • Each translator pins lean-runtime by commit. It moves the pin only after its own test suite passes.
  • The crate assumes a 64-bit platform. The expected values come from aarch64 Linux with glibc 2.39.
  • io compiles only on Linux, aarch64 and x86-64, because it models glibc.
  • The libm ports of cbrt, cbrtf, atanh and atanhf compile on every target. cbrt and cbrtf give the results of glibc 2.39's aarch64 build everywhere. atanh and atanhf use glibc's formula over the platform's log1p. On other platforms, the results can differ from native Lean on that platform. The owner chose one algorithm for every target.
