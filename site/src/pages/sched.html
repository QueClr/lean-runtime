The sched module

sched (feature sched) is Lean 4.34.0's task manager on one OS thread. Tasks are deferred and run as coroutines.

The scheduler came with batch sched-1. The task model is a decision of 2026-10-03 (Q5). It has deferred tasks, polling yield points and Lean's exit behaviour, and it switches stacks through corosensei. Batch sched-io adds cooperative blocking IO and the event loop.

The model

Native Lean runs tasks on a pool of worker threads. A worker may start a task at any time after it is made. It must finish the task before the task's value is needed. sched runs one of the schedules that such a pool can produce, on one thread.

A task runs at the first of these points:

  • It is needed. Task.get or IO.wait runs it on the stack of the code that needs it. It does so once the task is the head of the queue, which a free worker would start. Until then, the code waits, and the hub starts the heads on contexts of their own (sched-3).
  • The running code blocks (a sleep, a lock, a promise, a read of an empty pipe) and a worker is free. The task then starts on a context of its own. The number of workers is LEAN_NUM_THREADS, or the number of online processors.
  • An effect point. At an output, a flush, a process spawn or an exit, a task queued 5 ms ago or more goes first. Natively, a worker would have run it by then.
  • Polling. The program asks for the task's state again after a sleep, or 1000 times without one. Then the head of the queue starts on a context of its own, never on the stack of the code that polls.
  • main returns. finish runs the rest, as lean_finalize_task_manager does, with one fix (Exit).

A pure task that the program drops before it starts never runs: Lean deletes it.

What a waiter runs. Natively a waiting thread sleeps, and a free worker takes the head of the queue. So a waiter runs no task on its own stack except the one that a free worker would take now (sched-3, reviews AR-9 and AR-10). Another task there could block on something that only the waiter gives, and the program would hang where native ends. IO.waitAny runs a task of its list only when that task is the only unfinished one. While it waits, it keeps its worker, as native wait_any does.

Contexts and the hub

  • main's context runs on the thread's own stack.
  • Every other context is a corosensei coroutine. Its stack has the size of a native worker's stack: 1 GiB, or LEAN_STACK_SIZE_KB plus 128 KiB.
  • corosensei's coroutines are asymmetric: a coroutine suspends to the code that resumed it. So every switch goes through main's stack.
  • When main's context blocks, it runs the hub. The hub resumes the contexts that can go on, one at a time.

The hub picks, in this order:

  1. a context that can go on, in the order the contexts became able to;
  2. a queued task, on a new context, if a worker is free;
  3. a pure task that is marked started, when nothing else will happen;
  4. else, it waits in the event loop: until a descriptor is ready or the earliest sleeper or timer is due. With none of these, it waits forever (a deadlocked native program also waits forever).

Dependents. When a task finishes, its dependents are walked from the newest, as Lean's handle_finished walks them. A sync dependent runs at once, on the finishing context. The others are queued at their priority.

Task states

The pure-task rule

A pure task (Task.spawn, Task.map, Task.bind) has no effects. So it may run later, as on a slow worker.

  • The rule. Where a worker would start a pure task that no IO task waits for, the task is only marked started.
  • From then on, it cannot be deleted, and IO.getTaskState reports it running.
  • It runs at the first of these points:
    • it is needed, or it is polled;
    • an IO task comes to wait for it, also through other pure tasks;
    • nothing else can go on;
    • main returns.
  • Why. If a runaway pure task ran at once on a context, it could take the only thread. main, which natively goes on in parallel, would then wait.
  • Evidence. Three program cases with pure tasks each gave the recorded outcome in 20 of 20 native runs. lean2rr's own runtime fails one of them (runaway_pure_task_started); this rule passes it.
  • IO need. A pure task that an IO task waits for, directly or through other pure tasks, starts as an IO task does.
  • A started pure task keeps its worker until it runs (AR-25). Natively a worker runs its task to the end before it takes the next one. So a pure task behind it waits in the queue, and the program can still delete it. When a waiter needs that worker, the oldest started pure task runs on a context of its own. An IO task does not wait for started pure tasks.
  • A known difference (LSCHED-01). Natively, runaway pure tasks queued first can take every worker, for example the only one, and keep a later IO task from running. Here the IO task runs, because the pure task waits until the exit. The case runaway_pure_task_before_io accepts both outcomes.
  • A known difference (LSCHED-02). With two or more workers, a waiter can need a worker that a runaway started pure task keeps. Natively another worker takes the awaited task, and the waiter goes on. Here the runaway task runs first and never ends. The program hangs in both cases, because the exit waits for a started task. The case runaway_pure_before_awaited accepts both outcomes.
  • A known difference (LSCHED-03). A waiter can need a worker that a started pure task keeps while another worker only sleeps. Natively the sleeping worker can wake, finish its task and take the awaited task first. Here the started task runs at once, so the awaited task comes after the started task's run. If the started task reaches yield points, the sleeper goes on there, as natively. A wait for the sleeper instead could stop the program for as long as the sleeper sleeps, so that a watchdog fires. The case picked_task_sleeping_worker accepts both outcomes.

Yield points

A yield point lets other contexts go first, so that work that natively runs in parallel makes progress. The glue calls them from its externs:

  • effect() before an output, a flush, a process spawn and IO.Process.exit;
  • poll() at clock reads;
  • ref_read() at ST.Ref reads, only in programs that create tasks (each translator knows this when it translates). Every 1000th read polls; the others cost a countdown;
  • sleep_ms() for IO.sleep and dbgSleep.

IO.getTaskState and IO.checkCanceled poll by themselves. So while !(← IO.hasFinished t) do pure () ends, as it does natively.

Promises and Std.Sync

  • IO.Promise.new, resolve and the drop of an unresolved promise follow Lean. Only the first resolution stores a value.
  • Promise.result? needs no scheduler call: the glue returns the promise's own task. Task.pure needs none either: the glue makes a finished task that holds the value.
  • Promise.result! on a promise dropped without a value prints Lean's panic message. Then the context waits forever (option_get_or_block), as the native thread does.
  • When a task finishes, its sync dependents run first. The contexts that wait for it wake when that walk ends, or earlier when another task the program still holds finishes, as natively. One exception is a Lean bug (LB-32): when result! starts its endless wait, they wake at once.
  • sched::sync has Lean's BaseMutex, Condvar, BaseRecursiveMutex and BaseSharedMutex.
  • Std.Channel, Barrier, Semaphore and the rest of Std.Sync are Lean code over these and promises. They need nothing more.

The wait cores

Batch wait-1 moves three wait protocols into the crate. Before, each translator had its own copy. Each translator keeps its own memory layout and calls the crate.

CoreWhat it doesThe forms
Wait for a computationA context waits for a thunk, a static or a constant that another context computes. The value is computed once.A 4-byte Gate in the translator's cell, or keyed functions with no room in the cell.
The reference ruleST.Ref follows Lean 4.35: while modify holds a reference, every other operation on it waits.The type sched::Ref, or keyed functions around the translator's record.
Deferred resolutionA promise dropped inside a free is resolved after the free.DrainScope, defer and run_deferred, in both modes.

The rules for all three:

  • Waiters wake in the order they began to wait.
  • A wait keeps the worker, as a spinning native thread keeps its own.
  • A computation that needs itself waits forever, and the other contexts go on (LB-08).
  • A wait inside a free is a Rust panic with the reason. No Lean program reaches it, because a free runs no Lean code.

References. The thread that holds a reference in modify also waits when it reads it. Natively that read spins forever. A store from code nested in modify's function waits too, as in Lean 4.35. In the keyed form, the closing store is the store made in the same frame as the take.

Promises dropped in a free. Natively a sync dependent runs inside the free, when the free reaches its promise. The translators must not suspend inside a free, so the crate keeps the resolution in a list. The list runs when the free ends. It is moved out first, so a free inside a dependent resolves its own promises first, as natively. The case tasks/promise_nested_free_order checks this order. Inside one free, the order follows the translator's drops, which can differ from native's.

Each entry belongs to the context that dropped the promise, and only that context runs it. A translator must report the end of every free. Otherwise the entries wait for that context's next free or settle point, and debug builds report the missing call.

Exit

  1. main returns.
  2. finish sets Lean's shutdown flag and runs the remaining tasks. It waits until no task is queued or running, and no context but main's is left.
  3. The glue flushes the streams (io's exit order) and exits.

So a runaway task keeps the process alive, as natively. Dedicated tasks run to completion, as natively. A task whose dependency never finishes, such as an unresolved promise, is not waited for.

A pool task enqueued after main returns also runs. Natively it is lost once no pool worker is left (LB-13).

IO.Process.exit, also from a task, exits at once: no task is waited for.

Blocking IO and the event loop

Natively, a read of an empty pipe blocks only its own thread. The program's other threads go on. On one thread, the same read would stop every context. Batch sched-io (2026-10-04) makes such calls cooperate.

  • When. A blocking call cooperates when other contexts exist, a task is queued, or the event loop has a descriptor or a timer. Otherwise it is the plain system call, as before. A program without tasks pays one load of a flag per call.
  • Reads of pipes, FIFOs, sockets and terminals wait until the descriptor is readable, and let the other contexts run. Then they make the same read(2), which no longer blocks.
  • Writes to pipes and sockets try pwritev2 with RWF_NOWAIT, which writes what fits. On EAGAIN they wait until the descriptor is writable. A write to a terminal waits until it is writable, then writes the whole rest at once, as natively.
  • Handle.lock retries flock without blocking. Child.wait waits for the child's pidfd.
  • The same bytes and errors. Each call is the blocking call, made once it no longer blocks. Only the interleaving changes, to one that native's threads also allow.
  • Regular files never block, so their calls stay plain, as natively.
  • Stream locks. A task blocked in a read keeps its stream's lock, as glibc does. Another context that wants the stream waits for it without blocking the thread. This holds for a lock held across any wait.
  • Free and drop paths. Both translators mark them with a no-suspend scope. In the scope, the io calls never suspend the context. A dropped stream whose pipe is full is flushed when the scope ends.

The event loop

  • The scheduler's own, in src/sched/reactor.rs. It registers descriptors with epoll, native's own libuv loop descriptor when the glue opened it.
  • poll_fds is poll(2) for a context: the context blocks, and the loop wakes it.
  • timer_start and watch run a callback on the loop context, a context of its own, as libuv's loop thread is a thread of its own.
  • A watch holds its descriptor until unwatch. While its call is queued or running, the watch is out of epoll's set. So a callback that blocks does not make the hub spin.
  • The hub waits in epoll_wait when nothing can run. The polling and effect points look without waiting, at most once a millisecond.

Std.Internal.UV: the loop, timers and signals

  • src/sched/uv.rs has the externs of Std.Internal.UV.Loop, Timer and Signal.
  • A timer or a signal watcher resolves its promise on the loop context. So the promise's sync dependents run on a context of its own, as natively on libuv's thread.
  • Timers and watchers follow Lean's state machines: one-shot and repeating, next, reset, cancel and stop.
  • Every extern first lets the loop run what is due, as native's loop lock does.
  • Signals use signal-hook's safe API: flags, native's own signal pipe that the loop watches, and a conditional default action. When no watcher listens, a signal has its default action again, as natively. A second signal to a one-shot watcher takes the default action too, as libuv's reset handler does.
  • Recorded deviations: SIGIO ends the program with status 157 instead of its signal. SIGTSTP, SIGTTIN and SIGTTOU stop it with SIGSTOP.
  • Loop.alive is true, and Loop.configure changes nothing a program can see.

The cases in tests/cases/taskio/ hang or misorder without sched-io. Examples: IO.Process.output of a child that writes 300 000 bytes to stdout, and a task that reads cat's output while main writes to it. The cases in tests/cases/uvloop/ check the timers and signals; one sends SIGUSR1 to the program itself.

The unsafe step in the glue

sched has no unsafe code, except one native quirk behind its own feature (Stack overflow). The crate root denies unsafe, outside the files that UNSAFE.md lists. One step remains that safe code cannot do, so each translator's glue does it. The step is to suspend the running coroutine from deep inside a call. corosensei gives the coroutine's Yielder only to its top function, and nothing safe gives it to deeper code. So each translator's glue does one raw-pointer dereference, in Glue::suspend only:

fn suspend(&self, s: Suspend<'_>) {
    // SAFETY: lean-runtime docs/sched.md, "Why Glue::suspend is sound".
    unsafe { (*s.yielder()).suspend(()) }
}
  • The proof. docs/sched.md states it in full, with seven invariants (S1 to S7). Each invariant names the code that keeps it. leanrs's two checkers found it sound as documented (2026-10-04).
  • The checks. Miri cannot run corosensei's stack switch. So the argument rests on review, runtime assertions, the driver's integration tests, and AddressSanitizer runs by hand.
  • The glue's duties. The dereference stays in suspend; the pointer is not kept; scheduler functions run only on stacks that the scheduler knows.
  • Approval. The owner approved this design (2026-10-03): "rare justified unsafe is fine, but need to be documented well".
  • Alternatives were ruled out:
    • other coroutine crates: unsound APIs, unsafe constructors, or 2 MiB stacks;
    • OS threads that pass a baton: the jobs are not Send;
    • a scoped thread-local: coroutines do not nest as its scopes assume.

Stack overflow

Lean prints Stack overflow detected. Aborting. from a SIGSEGV handler, and aborts. It does this when the fault is in the guard page below the stack of the faulting thread. Here a task runs on a context, with a stack and a guard page of its own. Rust's handler does not know these guard pages, so the crate has its own handler (sched-3, AR-11), behind the feature stack-overflow. The feature is off by default, and lean2rr turns it on. Without it, a task that overflows its stack ends with a plain SIGSEGV (status 139).

  • The opt-in. The glue calls sched::install_stack_overflow_handler() once, on each thread that runs Lean code, before any Lean code runs there. It calls it from main, after Rust's runtime starts, and never from an ELF constructor. sched::start also registers its thread.
  • Earlier handlers. A fault that is not an overflow goes to the handler that was there before. The crate calls it as the kernel would: with its signal mask, and with the default action set first for a one-shot handler.
  • A record per thread. Each registered thread gets an alternate signal stack and a record. The record holds the guard of the thread's stack, and the guard of the context that runs now. The hub updates it at each switch.
  • The handler. It finds the record of the faulting thread by the address of its errno. It reads only atomics: no lock, no allocation, no thread-local. A fault in either guard gives Lean's message and an abort (status 134).
  • Other faults go to the handler that was there before (Rust's), or to the default action (status 139), as natively.

Installing a signal handler needs unsafe, so this is a native quirk, in stack_overflow.rs. docs/native-quirks.md has its proof. The proof covers the alternate stacks, the handler's async-signal safety, the moments between a publication and a switch, and the forward to the earlier handler.

Limits of one thread

  • A context that computes without a block or a yield point delays the others.
  • IO.waitAny does not pick the fastest of several running tasks.
  • A few blocking calls still block the one thread: open(2) of a FIFO, and a translator's own calls outside the crate. Its glue avoids the latter by waiting first, with poll_fds.
  • Another process's flock release is seen within 16 ms, not at once.

Threads mode has none of these limits: each task has a real thread.

Plans

Toward real threads

Decision (2026-10-03): "parallelism will be supported, not the focus now". Since 2026-10-04, threads mode (feature threads) is Lean's task manager on real threads, beside this scheduler. A build has one of the two. This scheduler stays the default.

  • Shared: the task-manager rules, such as the exit order and the walk of dependents. The names of the functions, and the program cases with their Rust ports, are also shared.
  • Only here: the coroutines, the hub, the yield points, the pure-task rule and sched-io's cooperative IO. Threads mode needs none of them, because a blocked task blocks only its own thread.

Costs to measure (O12)

Nothing in sched is timed yet. The timing session will measure:

  • the polling and effect points;
  • the two switches per handover;
  • the cost per task;
  • the memory that pooled stacks keep.
