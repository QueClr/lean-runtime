The test flow

Rows

A row is one function call with its expected result. Rows are [[row]] tables in tests/cases/<area>/<area>.rows.toml.

  • fn and args (Lean terms) name the call; expected is Lean's repr of the result.
  • A float row also has the exact bits, because repr loses NaN payloads and -0.0.
  • A panic row has the message, the default value and the stderr text. A row that ends the process has its stderr and exit status.
  • A row for a lifted limit (LB-04, LB-06, LB-11, LB-12, LB-37) expects the definition's result and records native's outcome beside it.
  • scripts/gen_rows.py writes the expected values. It runs scripts/oracle, a Lean program built natively with Lean 4.34.0.
  • tests/rows.rs and tests/rows2.rs run every row against the crate. Each Nat and Int row runs under four representations, so every word path and every slow path meets every value.
  • There are {{v:rows}} rows in {{v:row_areas}} areas.

Inputs come from argv or stdin. Both translators evaluate closed terms (CAFs, literals) when they translate. A test whose values are all literals never reaches the runtime. So the oracle reads its inputs at run time.

Program cases

A program case is a whole Lean program with a main.

  • Files: <id>.lean, and optional arguments, stdin, environment, a shell line (for closed descriptors, ulimit, pipes) and a starting directory tree.
  • scripts/cases.py expect builds the case natively and runs it 5 times. The results must be identical. It writes <id>.out, .err and .code.
  • A schedule-dependent case records every outcome seen; each one is allowed.
  • A case that natively never ends records the output before its timeout.
  • scripts/cases.py check --exe-dir DIR runs a translator's build of each case and compares it with the recorded files.
  • Each run starts in a fresh directory, with an empty environment, pipes for the three streams, a memory cap and a CPU-time limit.
  • There are {{v:cases}} program cases, in these areas:
      {{v:case_areas}}

A case may list documented deviations. For a translator's own deviation, the expected output stays native's, and the deviation's outcome is also allowed. The case's alternatives field can give that outcome to the one translator; then check does not allow it for the other translator. When native's outcome is a Lean bug, the case expects the correct outcome instead. It records native's outcome in a native field, which cases.py expect checks. check does not accept native's outcome there, so a return of the bug fails.

Rust twins

A twin is a Rust program that makes the same calls through lean-runtime as the case's Lean program makes through Lean's runtime. It adds only what a translator's glue adds.

  • tests/io_cases.rs has a twin for each case of the first io batch. It runs cases.py check on them, the same checker that the translators use.
  • tests/io2_cases.rs does the same for the cases of the second io batch, and for the debug/, clock/ and panics/ cases. The twins of the cases that set the process title run only with proc-title. tests/sched-driver has a twin for every tasks/, sync/, refs/, taskio/ and uvloop/ case, and for the io cases with tasks. Its twins run over sched and io, with a complete example of the glue. The glue runs main as the translators do: on a thread with Lean's stack size, or on the process's thread with LEAN_MAIN_USE_THREAD=0.
  • tests/sched-driver-mt runs the same twins of the tasks/, sync/, refs/ and taskio/ cases in threads mode. Each case runs 5 times, and every run must give a recorded outcome. In a threads build, the io twins and the uvloop/ twins also run inside tasks.
  • A few cases have no twin, because they test what a translator generates, for example whether its compiler folds a libm call. Their .toml says why.
  • So the crate is checked against native output before either translator adopts it.

The glibc differential test

  • tests/cfile_glibc.rs runs random sequences of Lean's handle operations. It runs each sequence on a real glibc FILE and on the model, each on its own copy of a file or pipe.
  • After every step, these must agree: the results (with the errno of an error), the end-of-file indicator, and the bytes on disk.
  • The oracle is glibc with one change: it flushes before a large read, as the model does (LB-02).
  • The test calls glibc through extern "C", which needs unsafe. That is test code only (UNSAFE.md).

Two more tests:

  • tests/libm_folding.rs needs no native recording. Each libm function must give the same bits on constant and on run-time operands, in an optimized build (semantics).
  • tests/io_rows.rs compares io scenarios with the output of a Lean probe built natively (tests/data/io_probe).

The check before each commit

scripts/check.sh runs before every commit:

  • the site check: the pages are up to date, with no broken link (site/build.py --check);
  • build, tests and clippy on the Rust toolchains of both translators, in every feature configuration (two of them with proc-title);
  • both scheduler drivers, in debug and release builds: the single-thread driver and the threads-mode driver;
  • formatting;
  • the plain-rustc builds that one translator uses, with its driver's cfg flags;
  • the libm folding test in a release build;
  • only with LEAN_RUNTIME_MIRI=1: Miri on the unsafe-fast configurations, one of them with proc-title and its native quirk;
  • a check that every file that allows unsafe has an entry in UNSAFE.md.

Miri is opt-in, because the default build has no unsafe code and Miri costs much CPU time (decision of 2026-10-04). Run it when an unsafe item changes. LEAN_RUNTIME_MIRI_FILTER limits it to the unit tests whose name holds a given text, such as argv_title.

Heavy steps run under a memory cap, and every test run has a deadline, because the host is shared.

Both translators

  • A change to the crate is gated by both projects' tests (decision O5).
  • Each translator checks its own builds of the cases with cases.py check.
  • Each translator pins the crate by commit. It moves the pin only after its own suite passes.
  • The work starts with a cross-test of the two translators' runtimes. Each disagreement is fixed in whichever runtime is wrong.
  • Each side runs the other's tests (decision Q9). The cases from lean2rr's cross-test of leanrs's fixtures are in folding/, io/, panics/ and cse/.

Reviews

  • Each batch gets a review from each project before it merges.
  • Each finding is judged before it is fixed.
  • A fix comes with a test that fails on the old code.
  • Every bug or disagreement becomes a test (decision O8). This is also true when the fix lands in a translator, if it concerns runtime behaviour.
  • A suspected bug in Lean's own runtime goes to a judge first (the rule).

Benchmark pairs

The speed floor (O12) needs measurements. The pairs exist; nothing is timed yet.

  • A pair is two programs that print the same checksum. One calls the crate's function as a translator calls it. The other does the same operation through Lean's own API, built natively.
  • The same work on both sides. The Rust side also does the glue's work, for example boxed Nat words and new string objects.
  • No folding. Only N, the number of iterations, comes from argv. The operands come from a fixed-seed generator and pass through an opaque sink (black_box, Bench.pin).
  • Counts: {{v:bench_pairs}} pairs for semantics ({{v:bench_not_comparable}} of them not comparable) and {{v:io_bench_pairs}} for io.
  • scripts/check_benches.sh builds both sides and compares the checksums. It times nothing.
  • Timing follows a fixed protocol: a host lock, one quiet core, nine alternating pairs, the median, and the peak memory beside it. A timing session runs only with the owner's approval.
