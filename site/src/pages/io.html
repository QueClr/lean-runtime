The io module

io (feature io) does what Lean 4.34.0's io.cpp and process.cpp do. It is safe Rust over std, rustix, nix and io-uring, except one native quirk (the process title). It copies the behaviour of glibc where a Lean program can see it.

The layers of a handle call

No bulk copies in the glue.

  • Writes take views (&[u8]).
  • read_uninit fills the caller's own uninitialized storage, with no zero pass. read fills initialized bytes; read_vec grows a Vec as the bytes come.
  • An unbounded result (a line, a path, an environment value) is appended to the caller's ByteSink.

The FILE model

Native Lean uses glibc's FILE for the standard streams and for every IO.FS.Handle. A Lean program can see that buffering:

  • in what reaches a descriptor, and when (another reader of the file, 2>&1 order, pipes);
  • in file positions (rewind, truncate, the stdin a program leaves to the next process);
  • in the sticky end-of-file and error indicators.

So CFile follows glibc 2.39's libio closely. It makes the same system calls in the same order, so it gets the same errno values. The documented exception is read_vec, which can split one read(2) of glibc's. From a regular file it makes two or three calls; from a device it reads in 64 KiB windows. The bytes and the position stay glibc's. It is safe Rust: the buffer is a Vec<u8>, and the buffer "pointers" are indices.

  • Get mode. A refill reads ahead from the descriptor. Lean reads from rp; the bytes up to re are read-ahead.
  • Put mode. The first write after a read starts the put area at the read position. Pending output waits in the buffer. It reaches the descriptor at a flush, when the buffer is full, before a read, or at exit.
  • Writing after reading. Before pending output goes out, the model seeks back over the read-ahead. So the bytes land at the position that Lean sees.
  • Buffer size. The descriptor's st_blksize when it is between 1 and 8191; otherwise 8192. A terminal is line-buffered. stderr is unbuffered.
  • LB-02. glibc drops pending output before a read of at least one buffer. lean-runtime writes the pending bytes first. Everything else on that path is glibc's.

A differential test runs random sequences of handle operations on real glibc and on the model, and compares them after every step (Testing).

Handles

  • A Handle is a CFile behind a std::sync::Mutex, as glibc locks each FILE.
  • The three standard streams are static and never close.
  • A file that the crate opened closes (fclose) when the last clone of its Handle goes away. A translator keeps the Handle inside its own object and drops it when it frees that object.
  • The crate keeps a list of open handles in glibc's order, for the exit. The list holds each file by a strong reference, and lets it go when the file's last handle goes away.
  • lock, tryLock and unlock wait in flock without the stream's lock, as native does.
  • In a program with tasks, a call that would block lets the other tasks run while it waits. Examples: a read of an empty pipe, a write into a full one, flock.
  • A task blocked in a read keeps its stream's lock. Another task that wants the stream waits for it without blocking the thread (sched-io, src/io/coop.rs).

Errors

  • IoError mirrors Lean's IO.Error: its 19 constructors in Lean's order, with plain fields. Each translator converts it to its own value.
  • decode_io_error maps an errno to libuv's code, picks the error class and libuv's message, and keeps the errno as the OS code. This is Lean 4.34's decoding in io.cpp.
  • decode_uv_error does the same for the operations that Lean implements with libuv.
  • The errno model. rustix does not touch libc's errno. So the crate keeps its own copy per thread, and sets it as the C call would. A program can see it: a later getLine on a stream with its error indicator set reports that errno.
  • LB-03. Some errors have no file name. When the error's class takes a file name (no such file, interrupted call), native Lean then crashes (SIGSEGV). lean-runtime gives the error with the file name "".

Files, directories, environment

  • Every file-system function first refuses a path that holds a NUL byte, as Lean does. The exception is setCurrentDir, which uses the part before the NUL, as Lean's C string does.
  • Paths are views: the bytes of a Lean string. Results of unbounded size (a path, a directory entry's name) go to the caller's ByteSink or callback, as bytes.
  • IO.getEnv, IO.appPath, the process id, IO.getRandomBytes, IO.sleep and the monotonic clock (Lean's absolute CLOCK_MONOTONIC) are in env.
  • dbgTrace prints its message to stderr and continues; dbgSleep sleeps (decision DV5). With streams, the message goes to the current stderr stream, as natively.
  • allocprof runs its action, then prints its message and a note on stderr. The note says that no data is available, because Lean's release runtime has no allocation statistics.

Processes

Native Lean forks, and the child calls execvp. Safe Rust cannot fork, so io::process spawns with posix_spawn (nix's safe wrapper). It then does what the forked child does before execvp:

  • sets up piped, inherited or null standard streams; a piped parent end becomes a Handle;
  • finds the program as glibc 2.39's execvp finds it;
  • builds the child's environment from the parent's environ, with Lean's changes applied in order;
  • enters the working directory in a spawner thread, so the parent's own directory does not change. Where the kernel refuses that, it changes the directory under a lock, then changes it back;
  • for a child that cannot start, starts a stand-in: a short /bin/sh with the child's streams. It writes the message on the child's stderr and exits with status 255, as Lean's forked child does.

wait, tryWait and kill follow process.cpp. IO.Process.output reads both pipes with poll. In a program with tasks, wait and output let the other tasks run while they wait (sched-io). Three Lean bugs are not copied. takeStdin keeps the setsid flag (LB-14). A null stream opens /dev/null close-on-exec in the parent, so nothing leaks (LB-15), and its failure is an error (LB-17).

Stream redirection

  • Natively, every thread has its own current standard streams. IO.setStdout replaces the calling thread's stream and returns the old one.
  • io::streams keeps these slots per thread. The slots are type-erased, because each translator has its own IO.FS.Stream value.
  • A task that runs as a coroutine has its own slots. The scheduler's glue swaps them at each switch.
  • The runtime's own stderr lines (panic messages, dbgTrace, timeit) go to the current stderr stream, as natively.

Startup descriptors

Before main, Lean's runtime starts libuv's loop. libuv 1.48.0 opens up to eight descriptors, close-on-exec, at the lowest free numbers. A program can see them: they decide which open fails first under a descriptor limit, and what a closed standard descriptor becomes. lean-runtime opens the same descriptors, with the same numbers, in the same order. The two io_uring rings are real rings, made as libuv makes them.

  • libuv decides whether to try the rings: Linux 5.10.186 or later, or as UV_USE_IO_URING says. The crate makes the same decision.
  • Then the kernel decides whether each ring exists. The crate makes the same io_uring_setup calls and keeps a ring only with the features that libuv needs. So a disabled io_uring, a seccomp filter or an old kernel leaves no ring, as natively.
  • The io-uring crate makes the rings, with libuv's parameters, and maps their memory as libuv does. The crate uses only its safe functions (UNSAFE.md has an audit).
  • So the ring's inode, its /proc/self/fdinfo lines, its four /proc/self/maps lines and its kernel thread (iou-sqp-<pid>) are native's. The epoll descriptor watches the polling ring, as natively.
  • One thing still differs. Native's loop thread starts the loop: its first round adds the signal pipe and the eventfd to epoll, through the control ring.
  • Glue duty. The descriptors must open before Rust's runtime starts, because Rust puts /dev/null on closed standard descriptors. So each translator's glue calls open_native_descriptors from an ELF constructor. That needs #[link_section], which deny(unsafe_code) refuses in the crate.
  • Glue duty. After the module initializers, the glue calls startup::mark_end_initialization, as the generated main does. Until then IO.initializing is true; in main it is false.
  • Native Lean ignores SIGPIPE before main, so a write to a pipe without a reader fails with EPIPE. Rust's own entry does the same for a Rust main. A glue whose entry is not Rust's (lean2rr's) ignores SIGPIPE itself.

The process title

Natively, IO.setProcessTitle writes the title over the process's original arguments (libuv 1.48). So /proc/self/cmdline and ps show the title.

  • The memory runs from argv[0] to the end of the last argument. A longer title is cut to that length less one byte, without an error. NUL bytes fill the rest.
  • The environment comes right after the arguments, and libuv does not move it. So a title can never grow past the arguments.
  • Lean's args come from libuv's copy of the arguments, so they do not change.

No safe API can write that memory. std returns copies of the arguments. The prctl calls that move the kernel's view are unsafe too: one needs a privilege, and the other resets the whole memory map. Writing /proc/self/mem would hide the same write from the compiler. So io::argv_title does it with unsafe code: a native quirk.

The file is built only with the feature proc-title, which lean2rr turns on. Without it, the crate has no unsafe code, and the title functions do this:

  • setProcessTitle fails with ENOBUFS, as libuv does when it holds no arguments' memory. A title with a NUL byte gives Lean's own error first. Nothing changes.
  • getProcessTitle gives argv[0], the title that a native program starts with.

With the feature:

  • The file has its own ELF constructor, so no glue takes part. glibc calls it with main's argc and argv, before main (glibc only: musl passes no arguments).
  • The constructor checks what it would write. In a shared library it writes nothing, and the title functions fail with ENOBUFS, as natively. A program started through the dynamic loader (ld.so ./prog) also writes nothing: a judged deviation (LQ1-01), since natively the title is written. In the program's executable it keeps the memory only if no other thread runs. The memory must also lie inside the kernel's span of the arguments (/proc/self/stat). Otherwise the title still behaves as natively, but /proc/self/cmdline keeps the arguments.
  • Like libuv, it copies the arguments and points the argument table at the copies. So std::env::args and main's argv keep the original arguments, as Lean's args do natively.
  • The file reads the table and the strings, writes the table's entries, and copies each new title over the arguments. Each unsafe block has a // SAFETY: comment.
  • UNSAFE.md has its entry, and docs/native-quirks.md its proof.

Exit

A native program ends through C's exit, which flushes the streams in a fixed order. The order is visible: a handle on /dev/stdout prints after main's own buffered output. The crate cannot register an atexit handler without unsafe, so the glue calls exit_flush (or exit) on every normal path.
